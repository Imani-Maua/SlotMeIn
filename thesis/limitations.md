# System Limitations

Known gaps between the current implementation and a production-ready scheduling system. Each entry names the limitation, explains why it exists, and notes what a full solution would require.

---

## 1. Coverage optimality vs. shift equity

**What the system does:** The CP-SAT scheduler maximises slot coverage and minimises over/underwork. On low-demand weeks where fewer shifts are available than there are staff members, the solver concentrates assignments on whoever is most available — typically always-available full-time staff.

**What it cannot do:** On low-occupancy weeks, the system has no mechanism to ensure shifts are distributed fairly before anyone receives a second shift-day. A staff member could receive three shifts in a week while an equally eligible colleague receives none, if that arrangement maximises coverage.

**Why:** CP-SAT optimises a single objective function. Fairness — equal distribution of shift-days across eligible staff — is not currently a term in that function. Coverage and fairness are in tension on low-demand days: the optimal coverage solution is not necessarily the fair one.

**What a full solution would require:**
- *Soft approach:* Add a penalty term for variance in shifts-per-week across eligible staff. The solver is nudged toward equal distribution but not hard-guaranteed.
- *Hard approach:* A two-phase solve — Phase 1 constrains each talent to at most one shift-day and fills what it can; Phase 2 removes the constraint and fills remaining gaps. This guarantees everyone gets one shift before anyone gets two, but requires running the solver twice and merging results.

This tension between coverage optimality and shift equity is an open problem in workforce scheduling literature and a natural extension of this work.

## 2. Staffing tier thresholds are unvalidated assumptions

**What the system does:** Morning tier is determined by hotel occupancy thresholds: ≤35% → LOW, 36–65% → MEDIUM, >65% → HIGH. The ML model was trained to reproduce these labels.

**What is unvalidated:** Whether these specific threshold values (35%, 65%) correctly reflect actual morning staffing demand at this restaurant. The thresholds were set by domain reasoning, not derived from observed operational data (covers served, revenue, staff hours).

**Why it matters:** The ML model's feature importances appear to confirm occupancy as the dominant morning signal — but this is circular. The model was trained on labels generated by the occupancy rule, so high occupancy importance is guaranteed by construction, not discovered from data.

**What a full solution would require:** Regression of actual morning operational metrics (covers served, table turns, revenue) against occupancy to empirically derive thresholds. This requires historical operational data the restaurant does not currently provide in structured form.

## 3. Afternoon distribution shift (~10% val→test gap)

**What the system does:** The afternoon tier model achieves 87.7% accuracy on real hotel test data across all model configurations and regularisation settings tried.

**What it cannot do:** Close the ~10% gap between simulation validation accuracy (~98%) and real-data test accuracy (~88%). This gap is structural — the simulation generates afternoon feature distributions (Resort Hotel occupancy patterns, Portuguese climate) that differ from the real Budapest restaurant's operating environment.

**Why:** The afternoon tier depends on multiple interacting signals (occupancy, day of week, season, temperature, special day). The simulation approximates these from a Portuguese resort dataset. The real restaurant is a Budapest city hotel. The feature-to-tier mapping is not identical across these two contexts.

**What a full solution would require:** Sufficient real labelled data (date, shift, observed tier) to train directly on the target domain, eliminating the need for simulation-based transfer. With the current ~840 real dates, this is marginal — a further 12–18 months of operational data would make direct training viable.

## 4. Staffing role counts have no frontend management UI

**What the system does:** The number of staff required per role at each tier (e.g., Server: LOW=2, MED=3, HIGH=4) is stored in the `staffing_rules` database table, with one row per role × tier combination. The `StaffingService` reads these counts from the database on each schedule run and seeds the table with defaults on first use. A `PATCH /staffing_rules/{role}/{tier}` API endpoint allows programmatic updates.

**What it cannot do:** Allow the manager to adjust these counts through the frontend UI without using the raw API. The 18 configurable cells (6 roles × 3 tiers) are accessible via API but there is no settings screen in the web application.

**What a full solution would require:** A settings page on the frontend that lists all role × tier combinations as editable number inputs and calls the PATCH endpoint on save. This is a small, well-scoped feature that would complete the management layer.

## 5. Occupancy and temperature must be supplied at schedule generation time

**What the system does:** The ML tier predictor requires `occupancy_pct` as input. If not supplied, the system falls back to a static day-of-week lookup (the pre-ML behaviour).

**What it cannot do:** Automatically source occupancy from the hotel's property management system (PMS) or forecast temperature from a weather API.

**What a full solution would require:** Integration with the hotel's PMS to pull the forecasted occupancy for the target week at generation time, and either a weather API integration or a seasonal temperature lookup table specific to Budapest. Until then, the manager must manually enter the occupancy figure when generating a schedule.

## 6. No empirical validation of objective weight ratios

**What the system does:** The five CP-SAT objective constants (FILL_WEIGHT, STEEP_OVERWORK_PENALTY, UNDERWORK_PENALTY, CONSTRAINED_FILL_BONUS, MILD_OVERWORK_PENALTY) are grounded in real wage data and financial reasoning. Their ratios are logically derived and documented.

**What is missing:** Empirical validation. The claim that the weights produce schedules a domain expert would approve has not been tested. A sensitivity analysis (±20% variation on each weight) would show whether the schedule output is stable, and expert elicitation (a manager reviewing sample schedules) would validate whether the priority ordering matches operational judgement.

**What a full solution would require:** Generate sample schedules under the current weights and ±20% variants, present them to the restaurant manager, and record preference judgements. This would either confirm the weights or provide grounded corrections.
